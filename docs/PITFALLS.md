# PITFALLS — 반복해서 걸린 함정들

**새 실수를 발견하면 이 파일 맨 아래에 항목을 추가하세요** — 무엇이 문제였고,
어떻게 알아챌 수 있고, 어떻게 피하는지 3줄 이내로.

아래 항목은 전부 **실제로 겪은 것**이다. 가정이나 예시가 아니다.

---

## 1. 시간대가 9시간 어긋난다 (수정 완료 — 재발 방지 게이트 있음)

- **문제**: `market.py` 의 장 시간 판정은 **한국시간** 09:00~15:30 기준인데,
  `live.py` · `jobs.py` · `streaming/` · `broker/` 는 `datetime.utcnow()` 로
  **UTC** 를 넘긴다. 저장소 전체에 시간대 변환이 한 줄도 없었다.
- **증상**: 장중(한국 09:30)에 `session=closed` 로 판정해 거래를 안 하고,
  한국시간 저녁 18:30(UTC 09:30)에 "장이 열렸다"고 판단한다.
- **피하는 법**: 시각이 필요하면 `market.now_kst()` 를 쓴다. `datetime.utcnow()`
  를 장 시간 판정 경로에 넘기지 않는다.
- **상태**: 수정 완료. `autotrader/` 안의 `datetime.utcnow()` 19곳을 전부
  `now_kst()` 로 바꿔 시스템이 하나의 시계를 쓴다.
- **재발 방지**: `tests/test_kst_clock_wiring.py` 가 AST 로 런타임 코드를 훑어
  `utcnow()` 호출이 하나라도 남으면 실패한다. 주석·독스트링의 언급은 세지 않는다.

## 2. 키움 `base_dt` 는 필수다 — 빈 값이 "오늘"이 아니다

- **문제**: `"base_dt": ""  # 오늘 기준` 이라고 적어 두었으나 추측이었다.
- **증상**: `return_code=2 입력 값 오류입니다[1511:필수 입력 값에 값이 존재하지
  않습니다. 필수입력 파라미터=base_dt]`
- **피하는 법**: 벤더 파라미터의 "빈 값이면 알아서 처리하겠지"를 믿지 않는다.
  실제 값(`now_kst().strftime("%Y%m%d")`)을 넣는다.

## 3. HTTP 200 인데 오류일 수 있다

- **문제**: 키움은 200 으로 응답하면서 본문에 `return_code` 를 담는다.
  코드가 그걸 확인하지 않아 업무 오류가 "데이터 없음"으로 둔갑했다.
- **증상**: 원인 불명의 `시세 없음`.
- **피하는 법**: `_inspect()` 를 거쳐 응답을 읽는다. 새 엔드포인트를 붙일 때도
  반드시 통과시킨다.

## 4. 응답의 배열 키 이름을 코드에 못박지 말 것

- **문제**: `js.get("stk_dt_pole_chart_qry", [])` 처럼 키를 고정해 두면 벤더
  응답의 키가 다를 때 **조용히 0건**이 되고, 그게 "데이터가 없다"로 보인다.
- **증상**: 인증도 통신도 성공했는데 봉이 0개.
- **피하는 법**: `_rows()` 를 쓴다 — 알려진 후보를 먼저 보고, 없으면 dict 를 담은
  첫 번째 리스트를 봉 배열로 찾아낸다.

## 5. `CsvProvider` 는 깨진 행을 조용히 버린다

- **문제**: 숫자 칸이 깨진 행은 말없이 건너뛰고, 날짜 칸이 깨지면 반대로 파일
  전체가 실패한다. 게다가 읽으면서 정렬해 원본의 순서 문제도 사라진다.
- **증상**: 500행 파일이 480봉이 되어도 아무 경고가 없다.
- **피하는 법**: 새로 수집한 캐시는 백테스트 전에 반드시
  `autotrader --csv <경로> validate-data` 를 통과시킨다. `dropped_rows` 가
  이 유실을 잡아낸다.

## 6. 실패를 개수로만 세지 말 것

- **문제**: `except DataError: fail += 1` 로 예외를 통째로 버렸다.
- **증상**: 첫 실전 수집이 `ok=0 fail=1` 한 줄만 남기고 끝났다. 원인을 알 수 없어
  고칠 수도 없었다.
- **피하는 법**: 루프에서 예외를 잡으면 **사유를 반드시 남긴다**
  (`last_failures` + 경고 로그). 삼키는 게 아니라 미루는 것이어야 한다.

## 7. 개발 환경에 깔린 패키지가 제약을 가린다

- **문제**: 개발 컨테이너에 `requests` 와 `yaml` 이 깔려 있어, 맨 `pytest` 통과가
  "stdlib 만으로 동작한다"는 증거가 되지 못했다.
- **증상**: CI 를 붙이자마자 맨 환경에서 **10개 테스트가 실패**했다. 테스트가
  `requests` 설치를 암묵적으로 가정하고 있었다.
- **피하는 법**: `python scripts/check_stdlib_only.py` 로 확인한다. 이 검사는
  임포트를 **차단한 채로** 돌기 때문에 패키지가 깔린 머신에서도 유효하다.

## 8. 전역 옵션은 하위 명령 **앞**에 쓴다

- **문제**: `--csv` `--config` `--threshold` `--votes` `--trail` 은 파서 자체에
  붙어 있다.
- **증상**: `autotrader backtest --threshold 0.45` → `unrecognized arguments`
- **피하는 법**: `autotrader --threshold 0.45 backtest` 순서로 쓴다.

## 9. 합성 데이터 성적은 아무것도 증명하지 않는다

- **문제**: 합성 데이터로 낸 백테스트 성적을 성과로 착각하기 쉽다.
- **증상**: "테스트 160개 통과"가 전략이 돈을 번다는 뜻으로 읽힌다.
- **피하는 법**: 합성 데이터 결과는 **코드가 돌아간다**는 증거일 뿐이다.
  판단은 실데이터 OOS 성적으로만 한다. `CLAUDE.md` 의 승격 경로를 따른다.

## 10. `zoneinfo` 를 쓰면 Windows 에서 깨진다

- **문제**: Windows 에는 IANA 시간대 DB 가 없어 `zoneinfo` 가 `tzdata` 패키지를
  요구한다. 그러면 stdlib 전용 제약이 깨진다.
- **피하는 법**: 한국은 서머타임이 없으므로 고정 오프셋으로 정확하다.
  `market.KST = timezone(timedelta(hours=9))` 를 쓴다.

## 11. 키움은 초당 1건만 받는다 (유량 제한)

- **문제**: 요청 사이에 대기가 전혀 없었고, 연속조회는 한 종목에 최대 30페이지를
  연달아 던진다. 429 를 재시도하지도 않았다.
- **증상**: `HTTP 429 허용된 API 요청 개수를 초과하였습니다 [유량=1, API ID=ka10081]`
  — 종목 하나만 요청해도 발생한다.
- **피하는 법**: 모든 키움 호출은 `_post()` 를 통과한다. 여기서 `min_interval`
  (기본 1.1초) 만큼 간격을 두고, 429 면 `Retry-After` 를 존중해 물러섰다가
  최대 3회 재시도한다. 계속 나면 `fetch --min-interval 2` 처럼 올린다.
- **주의**: 유니버스 전체(약 2,800종목)를 이 속도로 받으면 오래 걸린다. 실전
  운용은 매일 조금씩 누적하는 방식(cron `collect-daily`)을 전제로 한다.

## 12. 휴장일 표는 손으로 관리해서 반드시 틀린다

- **문제**: `market.KRX_HOLIDAYS` 는 하드코딩이라 검증 수단이 없었다.
- **증상**: 삼성전자 40년치 실데이터와 대조하니 3건이 어긋나 있었다 —
  2026-03-04(공휴일 아닌데 등재), 2025-01-27(설 임시공휴일 누락),
  2026-07-17(제헌절 부활 누락). 틀린 날짜 하나가 실제 거래일을 통째로
  건너뛰게 만든다.
- **피하는 법**: 시세를 수집한 뒤 `validate-data` 를 돌리고 두 경고를 본다.
  `bar_on_closed_day` = 표에 잘못 들어간 날, `missing_trading_days` = 표에서
  빠진 휴장일. 매년 초 이 대조를 반복한다.

## 13. 백테스트 구간이 코드에 박혀 있었다 (수정됨) + 실행 시간은 제곱으로 는다

- **문제**: `history(s, limit=u.lookback_days * 4)` 로 종목당 1,000봉만 쓰도록
  고정돼 있었다. 실데이터 40년치(10,914봉)를 수집해 놓고 91% 를 버렸고,
  그 결과 OOS 거래 표본이 4건까지 줄어 어떤 성과 지표도 의미를 잃었다.
- **피하는 법**: `backtest --bars N` 으로 구간을 지정한다. `--bars 0` 은 전부.
  미지정 시 기존 동작(1,000봉)을 유지하므로 예전 결과가 조용히 바뀌지 않는다.
- **주의 — 실행 시간**: 측정값(5종목 기준) 1,000봉 6초 · 2,500봉 38초 ·
  5,000봉 159초. 봉 수의 **제곱에 가깝게** 는다. 10,914봉이면 10분을 넘긴다.
  긴 구간을 돌릴 때는 먼저 짧게 확인하고 늘린다.
- **표본이 적을 때 지표를 믿지 말 것**: 거래 4건에서 나온 `profit_factor 20.9`
  는 통계가 아니라 우연이다. 노출도(`exposure_avg`)가 0.1% 대면 전략이 작동한
  게 아니라 거의 현금으로 있었다는 뜻이다. 두 값을 항상 함께 본다.

## 14. 토큰 응답의 `expires_dt` 는 "만료일" 이지 "남은 초" 가 아니다

- **문제**: `int(js.get("expires_in") or js.get("expires_dt", 43200))` 로 두 값을
  구분 없이 더했다. `expires_dt="20260825154600"` → 20조 초 ≈ 64만 년.
- **증상**: 토큰이 영원히 유효하다고 착각해 재발급하지 않는다. CLI 는 몇 초 만에
  끝나서 안 드러나지만, 크론으로 하루 종일 도는 LiveTrader 는 인증 실패로 멈춘다.
- **피하는 법**: `config.kiwoom_token_ttl()` 을 쓴다. 시세 어댑터와 주문 브로커
  양쪽에 같은 버그가 있었으므로 헬퍼를 한곳에 뒀다.

## 15. `strptime` 은 자릿수를 강제하지 않는다

- **문제**: `%m`·`%H`·`%M`·`%S` 가 1~2자리를 모두 허용한다. 그래서 12자리
  문자열이 14자리 형식으로 **조용히 잘못 파싱된다**.
  `"202608251546"` + `"%Y%m%d%H%M%S"` → 15시 **04분 06초** (15:46 이 아니다).
- **증상**: 그럴듯한 값이 나와 눈치채기 어렵다. 위 토큰 만료 계산에서 실제로
  23.3시간이 나왔다 (24시간이어야 함).
- **피하는 법**: 파싱한 뒤 `expiry.strftime(fmt) == 원문` 으로 되돌려 확인한다.

## 16. 유량 제한은 모드마다 다르다

- 공식 문서: 실서버 국내주식 조회 TR **1초당 5회**, 모의투자 **TR 1개당 1초 1회**.
- 모의 기준(1.1초)을 실서버에 그대로 쓰면 5배 느리다. `kiwoom_min_interval()` 이
  모드에 따라 고른다.
- **운영 주의**: 3개월간 **실서버** 미접속 시 API 사용이 자동 해지된다.
  모의투자만 쓰면 해지 대상이 될 수 있다 (공식 문서 "자동해지 조건").

## 17. 표본 20건대의 Profit Factor 는 신호가 아니라 잡음이다

- **실측**: 같은 전략·같은 데이터로 종목 수만 늘려가며 OOS PF 를 재봤다.

      거래  4건 → PF 20.93 (수익 -0.02%)
      거래 10건 → PF  3.25 (수익 +1.09%)
      거래 29건 → PF  0.84 (수익 -0.47%)
      거래 40건 → PF  0.59 (수익 -1.47%)

- **증상**: 표본이 작을 때 PF 가 터무니없이 크게 나온다. 손실 몇 건이 우연히
  작으면 분모가 작아져서다. "PF 20" 을 보고 좋은 전략이라고 판단하면 그대로
  실전에 올리게 된다.
- **피하는 법**: 승인 기준의 거래 수 하한을 50 으로 올렸고, **비용 차감 후
  순수익 > 0** 조건을 따로 뒀다. PF 가 1 을 넘어도 순수익은 음수일 수 있다.
- **함께 볼 것**: 노출도(`exposure_avg`). 1% 대면 전략이 작동한 게 아니라
  거의 현금으로 있었다는 뜻이라, 어떤 지표도 의미가 없다.

## 18. 무결성 검사는 "실제로 쓸 구간" 에 맞춰 돌린다

- **문제**: `validate-data` 는 파일 전체를 보는데 백테스트는 최근 일부만 쓴다.
  40년치 중 1985년 봉 하나가 깨져 있으면 FAIL 이 뜨는데, 그 봉은 쓰지도 않는다.
- **증상**: "FAIL 인데 무시해도 되는" 상태가 반복되면 게이트를 안 보게 된다 —
  게이트가 있으나 마나가 되는 가장 흔한 경로다.
- **피하는 법**: `validate-data --bars N` 으로 백테스트와 같은 구간만 검사한다.
  전체 이력 검사(`--bars 0`, 기본)는 수집 직후 한 번, 구간 검사는 백테스트
  직전에 돌린다. 실제로 20종목에서 1985~86년 깨진 봉 2건이 이렇게 갈렸다.

## 19. 백테스트가 나쁘다고 진입 로직부터 고치지 말 것

- **문제**: 20종목 백테스트가 OOS -1.47%(PF 0.59)였고 손절 청산이 72%였다.
  손절을 조일지 풀지 설정을 바꿔가며 찾는 것은 과최적화의 지름길이다.
- **실측**: `autotrader edge` 로 청산을 끄고 신호만 재보니 우위가 있었다.

      10일 지평선: 신호 +2.74% vs 기준선 +0.72% (우위 +2.02%, t=2.81)
      5일 안에 -2% 이하로 밀린 신호: 69.8%
      백테스트의 실제 손절: 평균 -1.87% 에서 발동, 보유 5.5일

  **우위 있는 신호 10건 중 7건이 손절선 아래로 내려간다.** 신호는 10~20일이
  지나야 값어치를 내는데 5.5일 만에 잘려나가고 있었다.
- **피하는 법**: 전략을 고치기 전에 `edge` 를 먼저 돌린다. 진입에 우위가
  없으면 청산을 아무리 손봐도 소용없고, 우위가 있으면 진입을 고칠 이유가 없다.
- **주의**: 앙상블 점수와 수익의 관계는 단조롭지 않았다(중간 구간이 가장 나쁨).
  점수로 포지션 크기를 조절할 근거가 아직 없다는 뜻이다.

## 20. 트레일링 스탑이 오늘 종가로 세운 스탑을 오늘 저가에 적용했다 (미래 정보)

- **문제**: `PaperBroker.mark` 가 청산 판정 **전에** `update_trailing` 을 불렀다.
  오늘 종가로 계산한 스탑이 같은 봉의 저가에 즉시 적용된다.
- **증상**: 하루 내내 오르기만 한 봉(시가 100 → 고가 120 → 종가 120)에서도
  종가로 세운 스탑 108 이 그날 저가 100 에 걸려 **손실 청산**이 기록됐다.
  종가가 나오기 전에는 그 스탑을 세울 수 없다 — CLAUDE.md 불변조건 1 위반.
- **영향**: 이 한 줄이 백테스트 결과를 통째로 뒤집었다.

      수정 전  OOS -1.47%  PF 0.59  승률 27.5%
      수정 후  OOS +5.71%  PF 3.02  승률 58.1%

- **피하는 법**: 상태 갱신은 그 봉의 판정이 **끝난 뒤**에 한다. 새 스탑은 다음
  봉부터 유효하다. 지표든 스탑이든, 오늘 종가에서 나온 값을 오늘 체결에 쓰면
  미래 정보다.

## 21. 청산 사유를 뭉뚱그리면 오진한다

- **문제**: 트레일링이 `pos.stop_price` 를 덮어쓰는데 청산 사유는 초기 손절과
  똑같이 `"stop"` 으로 기록됐다.
- **증상**: "손절 청산 72%, 평균 -1.87%" 를 보고 "ATR 손절이 좁다" 고 오진했다.
  실제로 전략의 초기 손절은 진입가 대비 -16.5% 로 넉넉했고, 5% 트레일링이
  그것을 조이고 있었다. 라벨을 나누자 초기 손절은 6% 에 불과했다.
- **덤**: `cooldown.COOLDOWN_EXEMPT_REASONS` 는 이미 `{"target", "trail"}` 로
  트레일링을 면제 대상에 두고 있었는데, 브로커가 `"trail"` 을 한 번도 내보내지
  않아 모든 트레일링 청산에 쿨다운이 걸리고 있었다.
- **피하는 법**: 서로 다른 원인을 같은 이름으로 기록하지 않는다. 오늘만 이
  패턴으로 세 번 시간을 썼다 (수집 실패 사유, 유실된 행, 청산 사유).

## 22. 트레일링 폭을 넓히자 하드스톱이 그 역할을 대신 받았다

- **변경**: 고정 5% → 진입 시점 ATR × √10 (종목·시점별 5.4~14.1%).
- **의도대로 된 것**: 트레일 청산 73 → 28건, 목표달성 48 → 61건, 기간만료
  11 → 30건. 포지션이 더 오래 살아남아 신호가 발현될 시간을 얻었다.
- **예상 못 한 것**: `hard_stop` 이 13 → 23건으로 늘었다. 트레일이 하던 방어를
  계좌 보호선(-10%)이 대신 받는다. 평균 -10.24% 짜리 청산이라 개선 폭을 깎는다.
- **판단**: 성능 개선이라고 부르지 않는다. TRAIN 은 +2.50% → +4.00% 로 좋아졌지만
  **VAL 은 -1.34% → -1.48% 로 차이가 없다.** 진짜 우위라면 다른 구간에서도
  나타나야 한다. 구조가 가설대로 바뀐 것까지가 확인된 사실이다.
- **다음에 볼 것**: 트레일이 아니라 손절·하드스톱의 역할 분담. 트레일을 넓히니
  하드스톱이 받아내는 구조라면 그 둘이 정리돼 있지 않은 것이다.

## 23. 지표를 매 봉마다 전체 재계산하면 봉 수의 제곱으로 느려진다

- **문제**: 전략이 `bars = list(ctx.bars[:ctx.at+1])` 로 앞부분을 복사한 뒤
  그 전체에 대해 지표를 계산했다. 봉마다 반복하니 O(n²).
- **측정**: 전체 53초 중 52초가 지표. `atr` 25초(`true_range` 21초), `rsi` 12초,
  `sma` 10초. `max()` 호출만 4,300만 회.
- **고친 방법**: 지표들이 **인과적**이라는 성질을 이용했다 — index i 의 값이
  i 이하 데이터만 쓰므로, 전체를 한 번 계산해 `[at]` 을 읽은 값과 앞부분만
  잘라 계산한 마지막 값이 **정확히** 같다(부동소수점 오차도 0). 종목별 캐시를
  `StrategyContext.cache` 로 넘기고 `ind.atr_at(ctx, p)` 류 접근자를 쓴다.
- **결과**: 20종목 2500봉 147초 → 8.2초 (18배). 봉 수에 대해 선형이 됐다.
  거래 목록과 최종 자산이 소수점 8자리까지 동일한 것을 확인했다.

## 24. 변수의 의미가 바뀌면 그 변수를 쓰는 모든 곳이 위험하다

- **문제**: 위 최적화에서 `closes = ind.closes(bars)`(앞부분)를
  `ind.closes_at(ctx)`(**전체 시리즈**)로 바꿨다. 이름은 그대로인데 의미가
  바뀌었다.
- **증상**: `swing_trend` 의 `ind.roc(closes, min(120, len(closes)-1))[-1]` 이
  전체 길이를 세고 **마지막 봉**을 읽게 됐다 — 미래 정보다. 테스트 224개가
  전부 통과해서 잡히지 않았다.
- **피하는 법**: 의미가 바뀌는 리팩터링에서는 그 변수를 쓰는 **모든 지점을
  기계적으로 훑는다** (`grep "closes\[" "len(closes)"`). 안 쓰게 된 변수는
  지운다 — 남겨두면 다음 사람이 옛 의미로 읽는다.

## 25. 중첩 구간 수익률로 t값을 계산하면 √h 배 부풀려진다

- **문제**: `edge` 가 h일 수익률을 매 봉마다 재고 표본 n 을 전부 독립으로 셌다.
  이웃 표본이 h-1 일을 공유하므로 독립이 아니다.
- **증상**: 10일 지평선 t=2.81 "유의" → 보정 후 **0.89 "우연과 구분 불가"**.
  247건 중 실질 독립 표본은 약 25건이었다.
- **이 값이 이미 소비됐다**: "신호는 10일에서 유의" 를 근거로 트레일 배수 √10 을
  정했다. 근거가 사라졌다 (다만 "5% = 1.5×ATR 은 이틀치라 좁다" 는 별개 근거는
  여전히 성립한다).
- **피하는 법**: `effective_n = n / horizon` 으로 보정한다. 지평선을 여러 개
  재고 그중 최대 t 로 판정하면 다중비교라 또 부풀려진다 — 게이트는
  `--gate-horizon` 으로 하나를 정해 그것만 본다.

## 26. `abs(t)` 를 쓰면 역효과 신호가 "유의" 로 찍힌다

- **증상**: 신호가 기준선보다 **나쁜** 경우(t=-1.39)에도 "약함" 으로 표시됐다.
  우위가 없는 정도가 아니라 반대로 작동하는데 긍정으로 읽힌다.
- **피하는 법**: 부호를 유지하고 음수는 "역효과" 로 따로 표시한다.

## 27. 백테스트와 실매매가 다른 규칙으로 돌면 승격 경로가 무의미하다

- **문제**: 종목별 ATR 트레일을 백테스터에만 연결하고 `live.py` 에는 빠뜨렸다.
  페이퍼는 계좌 기본값(고정 5%)으로 돌았다.
- **증상**: "백테스트에서 검증하고 페이퍼로 재현한다" 가 성립하지 않는다.
  테스트는 전부 통과한다 — 둘이 다른 값을 쓰는지 아무도 확인하지 않았으니까.
- **피하는 법**: 계산기를 한 곳(`indicators.atr_trail_pct`)에 두고 양쪽이
  같은 함수를 부르게 한다. 값을 두 곳에서 만들면 반드시 갈라진다.

## 28. 조용한 성공 — 게이트가 통과시킨 게 아니라 아무것도 안 한 것

같은 실패 양식이 여러 곳에 있었다. 전부 "실패했는데 종료코드 0" 이다.
크론·CI 는 종료코드만 보고 다음 단계로 넘어가므로, 조용한 성공은 시끄러운
실패보다 훨씬 비싸다.

- `fetch` 가 유니버스 0건이면 아무것도 안 하고 0 을 줬다 → 다음 단계가 빈
  캐시로 돈다. 이제 종목이 없으면 2, 전부 실패면 2(부분 실패 1과 구분).
- `validate-data` 가 `except DataError` 만 잡아서, cp949 로 저장된 CSV 하나가
  `UnicodeDecodeError` 로 명령 전체를 죽였다. 나머지 99종목의 검사 결과까지
  사라진다 → 게이트가 게이트를 못 한다. 이제 unreadable 로 기록하고 계속한다.
- `{종목}_5m.csv` 분봉 캐시를 일봉 종목으로 집어와 duplicate_date ERROR 가
  무더기로 났다. 멀쩡한 폴더가 FAIL 로 찍히면 게이트를 무시하는 습관이 생긴다.
- `DataQualityChecker` 가 `date.today()` 를 썼다. UTC 컨테이너에서 KST 밤 9시
  이후면 어제가 나와, 오늘 수집한 봉이 future_bar ERROR 가 된다.

## 29. 끄는 옵션이 안 꺼진다

`--trail 0` 은 "트레일링 끄기" 로 읽히는데, ATR 트레일이 별도 설정이라
종목별 폭이 그대로 붙었다. 끄려고 준 옵션이 안 꺼지면 A/B 실험 결과를 통째로
잘못 읽는다. 기능을 나눌 때는 **끄는 경로도 함께 나눠야 한다.**

## 30. 미래 정보는 전략별 테스트가 아니라 일반 게이트로 막는다

PITFALLS #24 의 버그를 224개 테스트가 놓쳤다. 전략 하나하나에 테스트를 더
붙이는 방식으로는 다음 번에도 놓친다.

`tests/test_no_lookahead.py` 는 전략 내부를 보지 않는다. **같은 `at` 에 대해
뒤에 미래 봉이 붙어 있든, 잘려 있든, 5배로 조작돼 있든 판단이 같아야 한다.**
전략이 늘어나면 자동으로 함께 검사된다(`_default_strategies()` 를 돈다).

잘라내기만 하면 `bars[-1]` 이 우연히 맞아떨어지는 구간이 생기므로, 미래를
**덮어쓰는** 검사를 함께 둔다.

## 31. 일괄 청산도 청산이다

`flat_at_time` 의 EOD 일괄 청산 경로가 `risk.register_exit` 만 부르고
`cooldown.register_exit` 는 부르지 않았다. 손실로 강제 정리한 종목에 다음 날
아침 바로 되들어간다 — 규율로 자른 것을 규율 없이 되사는 셈이다.
청산 경로를 새로 만들 때는 **기존 청산 경로가 부르는 것을 전부 부르는지**
대조한다.

## 32. 접수(ACCEPTED)를 체결(FILLED)로 취급하면 유령 포지션이 생긴다

`KiwoomBroker.submit()` 이 주문 접수 응답에서 곧바로 `Fill` 을 만들어 돌려줬다.
그러면 이 셋이 전부 "전량 체결" 로 기록된다:

- 호가창에 걸려만 있는 미체결 주문
- 100주 중 30주만 나간 부분체결
- 증거금 부족으로 **거부된** 주문

포트폴리오는 있지도 않은 포지션을 들고 있다고 믿고, RiskEngine 은 그 허구
위에서 다음 진입을 판단한다. 백테스트에서는 이 구분이 필요 없지만(같은 봉에서
즉시 체결로 모델링한다) 실계좌에서는 이것이 곧 손실이다.

`autotrader/orders.py` 의 상태머신으로 분리했다. 거부는 **예외가 아니라
상태**다 — 예외로 던지면 호출부가 "주문이 안 나갔다"(네트워크 실패)와
"브로커가 거부했다"를 구분하지 못한다.

## 33. 재연결 한 번에 보유수량이 두 배가 된다

WebSocket 이 끊겼다 붙으면 브로커가 놓친 체결통보를 다시 밀어준다. 이것은
**정상 동작**이다. 중복을 걸러내지 못하면 같은 체결이 두 번 반영된다.

`ExecutionReport.exec_id` 로 걸러낸다. 방어가 두 겹이다:

1. 이미 본 `exec_id` 는 무시
2. 주문 수량을 넘는 체결은 거부 (`min(filled_qty, remaining)`)

`exec_id` 를 안 주는 브로커가 있을 수 있어 2번이 따로 필요하다.

## 34. 종료 상태에서 나가는 길을 열어두면 죽은 주문이 되살아난다

늦게 도착한 낡은 "접수" 통보가 이미 체결된 주문의 상태를 되돌리면, 포지션이
유령처럼 되살아난다. 전이표에서 `FILLED`/`CANCELLED`/`REJECTED`/`EXPIRED` 의
출구를 전부 비워 뒀고, 표에 없는 전이는 조용히 넘기지 않고 `OrderStateError`
를 던진다 — 대개 진짜 버그의 첫 신호다.

취소 "요청"과 취소 "완료"도 다르다. `CANCEL_REQUESTED` 를 종료로 취급하면
그 사이에 일어난 체결을 놓친다.

## 35. 청산 규칙이 페이퍼 브로커 안에만 있으면 실계좌에서 스탑이 안 걸린다

손절·트레일링·타깃·시간청산이 전부 `PaperBroker.mark()` 안에 있었고,
`live.py` 의 그 블록은 통째로 `isinstance(broker, PaperBroker)` 안이었다.
**실브로커로 돌리면 청산이 하나도 동작하지 않는다.**

백테스트에서 검증한 것과 전혀 다른 것이 실계좌에서 도는데 겉으로는 같아
보인다 — 승격 경로에서 가장 위험한 종류의 불일치다.

`autotrader/exits.py` 로 **판정**을 꺼냈다. 판정과 집행을 나누면 페이퍼는
자기 포트폴리오에 즉시 적용하고, 실계좌는 청산 **주문**을 낸다. 봉 판정
(`evaluate_exit`)과 실시간 판정(`evaluate_exit_live`)의 우선순위가 같아야
한다 — 다르면 페이퍼에서 검증한 청산이 실계좌에서 다른 순서로 일어난다.

트레일링도 같은 함정이다. 스탑을 끌어올리는 주체가 `mark()` 안에만 있어서
실계좌에서는 트레일링이 **이름만 남아 있었다**. `update_trailing_stop` 으로
꺼내 양쪽이 같은 함수를 부르게 했다.

## 36. 실계좌에서 "청산 판정" 과 "청산 완료" 는 다르다

`_dispatch_real_exits` 는 주문을 낼 뿐 risk/cooldown/tracker 를 건드리지
않는다. 체결도 안 됐는데 손익을 기록하면 그것이 곧 유령 포지션이다
(#32 의 반대 방향 실수).

시세 조회 실패도 조용히 넘기면 안 된다 — 스탑이 걸려야 할 포지션이 방치된다.

## 37. 중복 주문은 결정적 id 로 막는다

`entry_order_id(전략, 종목, 신호시각, 방향)` 은 같은 신호에 항상 같은 값을
낸다. 재시도·재시작·스트림 중복 어디에서 와도 장부가 "이미 낸 주문" 으로
알아본다.

신호 시각을 **분 단위로 자른다.** 초 단위로 다르게 찍히면 id 가 달라져
중복 방지가 뚫린다. 사이클이 분보다 자주 돌면 이 정밀도를 올려야 한다.

청산 id 에는 포지션 **진입 시각**을 섞는다. 같은 종목을 팔았다 다시 사서 또
팔 때 두 청산이 같은 id 를 갖지 않게 하기 위해서다.

## 38. 배선을 검사하지 않으면 함수만 맞고 호출이 틀린다

`_dispatch_real_exits` 를 직접 부르는 테스트는 전부 통과하는데, `cycle()` 이
그것을 부르지 않으면 아무 소용이 없다 — 그것이 원래 버그의 정확한 모양이었다.

`cycle()` 을 통째로 돌리는 테스트를 넣자마자 **정의되지 않은 이름(`marks`)**
이 튀어나왔다. 실브로커면 런타임에 그대로 죽는 코드였고, 단위 테스트 346개가
전부 통과하고 있었다. 경로가 갈리는 코드는 갈린 쪽을 실제로 통과시켜 봐야 한다.

## 39. 재시작 복구는 "덮어쓰기" 가 아니라 "합치기" 다

두 종류의 진실이 있고 섞으면 안 된다.

**브로커만 아는 것** — 보유수량, 평균매입가, 현금, 체결 여부. 우리 로그가
뭐라 하든 브로커가 이긴다. 다른 단말에서 손으로 팔았을 수도, 우리가 죽어
있는 동안 체결됐을 수도 있다.

**우리만 아는 것** — 손절가, 목표가, 트레일 폭, 진입 시각, 최고가 기록.
**브로커 잔고에는 이것들이 없다.** 기록해 두지 않으면 재시작 이후 그 포지션에는
스탑이 영원히 걸리지 않는다.

그래서 브로커 잔고를 뼈대로 삼고, 우리 기록에서 브로커가 모르는 값만 채운다.

브로커에 없는 종목은 버린다(정리된 것). **브로커에 있는데 우리가 모르는
종목은 버리지 않는다** — 버리면 그 포지션은 영영 청산되지 않는다. 대신
"손절선을 모른다" 고 경고로 드러낸다.

`KiwoomBroker.positions()` 가 `opened_at=now_kst()` 를 넣는 것에 주의. 브로커
잔고에는 진입 시각이 없어서 어쩔 수 없는데, 이 값을 그대로 쓰면 조회할 때마다
"방금 샀다" 가 되어 보유기간 청산이 영원히 안 걸리고 청산 주문 id 도 매번
바뀐다. 복구가 이 값을 반드시 덮어써야 한다.

## 40. 상태 저장은 임시 파일에 쓰고 갈아끼운다

같은 파일에 곧바로 쓰면 전원이 나갔을 때 반쯤 쓰인 JSON 이 남고, 다음 기동에서
상태를 통째로 잃는다 — 손절선까지 함께. `path.tmp` 에 쓰고 `os.replace` 한다.

반대로 상태 파일이 깨졌다고 매매를 못 하면 안 된다. 빈 상태로 시작하면 브로커
잔고는 그대로 살아 있고, 잃는 것은 우리 기록뿐이며 그건 복구 경고가 드러낸다.

저장은 **매 사이클 끝**에 한다. 종료 시점에만 저장하면 강제 종료·정전에서 그
사이 진입한 포지션의 손절선을 통째로 잃는다.

## 41. 데이터가 없으면 코드가 있어도 조용히 죽어 있다

`reconcile` 이 수량 변화를 보고하는 코드는 처음부터 있었는데,
`snapshot_positions` 가 `qty` 를 담지 않아서 **한 번도 발동하지 않았다.**
`m.get("qty", bp.qty)` 가 항상 기본값으로 떨어지니 언제나 "변화 없음" 이다.

변이 테스트로 발견했다 — 그 줄을 망가뜨렸는데 테스트가 그대로 통과했다.
"고쳐도 테스트가 안 변하면, 그 코드는 원래 아무 일도 안 하고 있었던 것" 이다.

## 42. 인증 실패는 인증 실패라고 말한다

키움은 앱키가 틀려도 **HTTP 200** 을 준다. `return_code` 로만 구분된다.
곧바로 `js["token"]` 을 읽으면 `KeyError: 'token'` 이 나고, 사용자는 앱키가
틀렸는지 서버가 이상한지 우리 코드가 깨졌는지 알 수 없다.

`return_code` 와 토큰 존재를 확인하고, 무엇을 고쳐야 하는지(앱키·모드)까지
메시지에 넣는다.

## 43. `capture_output=True` 는 stdin 을 상속한다 — Windows 에서 터진다

`subprocess.run(..., capture_output=True)` 는 stdout/stderr 만 파이프로 잡고
**stdin 은 부모에서 그대로 상속**한다. pytest 캡처 아래의 Windows 에서는
부모의 stdin 핸들이 유효하지 않을 수 있고, 그러면 핸들 복제에서 죽는다:

```
OSError: [WinError 6] 핸들이 잘못되었습니다
  subprocess.py: _make_inheritable → _winapi.DuplicateHandle
```

Windows + Python 3.14 에서 `test_stdlib_only.py` 만 이렇게 실패했다. 리눅스
개발 환경에서는 재현되지 않는다 — **사용자 환경에서만 깨지는 종류**다.

자식이 입력을 읽지 않는다면 `stdin=subprocess.DEVNULL` 을 명시한다.

## 44. Windows 의 TEMP 가 남의 폴더를 가리킬 수 있다

사용자 환경에서 `TEMP` 가 `C:\Users\Public\Documents\ESTsoft\CreatorTemp`
(알집 계열 프로그램이 만든 경로)로 잡혀 있어 **쓰기 권한이 없었고**, pytest 의
`tmp_path` 를 쓰는 테스트 50개가 한꺼번에 `PermissionError` 로 죽었다.

코드 문제가 아니므로 고칠 것은 없지만, 사용자가 "테스트가 50개 실패한다" 고
가져왔을 때 **코드를 뒤지기 전에 이것부터 의심한다.** 우회는 이렇게 한다:

```powershell
python -m pytest -q --basetemp="$env:USERPROFILE\AppData\Local\Temp\pytest"
```

오류 메시지에 `Public\Documents` 나 낯선 회사 이름이 보이면 이 경우다.

## 45. 콘솔에선 되고 파이프로 넘기면 죽는다 (cp949)

파이썬은 **콘솔에 직접** 쓸 때 Windows 유니코드 콘솔 API 를 쓰지만, 출력이
**파이프로 넘어가면** locale 기본 인코딩으로 떨어진다. 한글 Windows 에서
그것은 cp949 이고 `—`(U+2014) `✓`(U+2713) `ó` 가 거기 없다.

```
UnicodeEncodeError: 'cp949' codec can't encode character '✓'
```

실제로 겪은 모습이 헷갈린다:

- `python -m autotrader lowturnover` → 콘솔 → **정상**
- 같은 코드를 `subprocess.run(..., capture_output=True)` 로 → 파이프 → **죽음**
- `> out.txt` 나 `| Select-String` 도 마찬가지

그래서 "내 화면에선 잘 되는데" 가 성립한다. #43 을 고쳐 WinError 6 이 사라지자
그 뒤에 가려져 있던 이 문제가 드러났다.

**소스를 눈으로 훑는 검사로는 못 잡는다.** 주석 속 `—` 는 무해하고 `print` 로
나가는 것만 문제인데, 그 둘을 정적으로 가르기 어렵다. 실제로 cp949 파이프를
만들어 실행하는 테스트만이 잡는다 (`tests/test_cp949_output.py`,
`PYTHONIOENCODING=cp949`).

대응은 두 갈래로 나눴다:

- **진단 스크립트**(`scripts/check_stdlib_only.py`)는 출력을 ASCII 로 제한한다.
  환경이 이상할 때 돌리는 물건이라 어떤 인코딩에서도 읽혀야 한다.
  `✓`/`✗` → `[OK]`/`[FAIL]`.
- **CLI 리포트**는 한국어라 ASCII 제한이 비현실적이다. 대신 진입점에서
  `sys.stdout.reconfigure(errors="replace")` 로 **인코딩 실패를 치명적이지
  않게** 만든다. 못 쓰는 글자는 물음표가 되지만 결과는 나온다 — 리포트 한
  글자 때문에 실행 전체가 죽는 것보다 낫다.

## 46. cron 의 요일은 0=일, 파이썬은 0=월

`scheduler.py` 는 `datetime.weekday()` 를 쓴다 — **0=월** … 6=일. 표준 cron
(`crontab(5)`)은 **0=일** 이다. 한 칸이 어긋난다.

```
"0 15 * * 0-4"   내부 해석 → 월·화·수·목·금
                 cron 해석 → 일·월·화·수·목
```

**금요일이 통째로 빠지고 일요일에 헛돈다.** 장이 열리는 날의 20% 를 매주 잃는데
크론은 아무 소리도 내지 않는다. 로그에도 "금요일에 아무 일도 없었다" 로만
보여서, 데이터가 이상하다고 의심하기 전까지는 원인에 도달하지 못한다.

내부에서 `0-4` 를 쓰는 것 자체는 옳다. 잘못은 **변환 없이 내보내는 것**이다.
`CronExpr.to_crontab_expression()` 이 요일 필드만 바꾼다. 나머지 필드는 원문
그대로 둔다 — `*/5` 를 `0,5,10,...` 으로 풀면 사람이 crontab 을 읽고 검토할 수
없게 된다.

기존 테스트가 이 버그를 **정답으로 박아 두고** 있었다는 점이 더 중요하다
(`"0 15 * * 0-4 run j1" in lines[0]` 을 통과 조건으로 삼았다). 테스트가 있다는
사실 자체는 그 동작이 옳다는 증거가 아니다. `tests/test_cron_weekday_export.py`
가 `autotrader schedule` 출력 전체에 대한 게이트를 건다.

## 47. PaperBroker 는 프로세스가 끝나면 잔고가 사라진다

`recovery.SessionState` 는 "브로커에 물어볼 수 없는 것만 담는다" 는 계약이다.
실브로커에서는 옳다 — 현금·수량·평균단가는 증권사가 진실이고, 우리도 저장하면
두 진실이 생겨 어긋났을 때 어느 쪽이 맞는지 알 수 없다.

그런데 `PaperBroker` 는 그 브로커가 **우리 프로세스 안에** 있다. 크론이 매일 새
프로세스로 부르면:

```
1일차  매수 10주 → cash 9,298,895
2일차  reconcile_positions → "기록에 있으나 브로커에 없음 — 정리된 것으로 본다"
       → 포지션 소멸, cash 는 initial_cash 로 복귀
```

경고 문구는 나온다. 다만 의미가 반대다 — 실브로커라면 "브로커에 없다 = 정리됐다"
가 맞지만, 페이퍼는 그 상태 파일이 유일한 진실이다. **60거래일을 돌려도 매일
1일차라 측정되는 것이 없다.**

`broker/paper_state.py` 가 현금·포지션·청산기록·체결기록을 파일에 둔다.
`LiveTrader.recover()` 는 이것을 reconcile **보다 먼저** 복원한다. 순서를
뒤집으면 reconcile 이 빈 브로커를 보고 같은 버그가 재현된다.

계좌 파일이 깨졌을 때는 `SessionState` 와 달리 **예외를 던진다.** SessionState 는
같은 상황에서 빈 상태로 넘어가는데, 그건 브로커에 진짜 잔고가 남아 있어서 잃는
것이 손절선뿐이기 때문이다. 여기서는 그 파일이 잔고 자체라 조용히 넘어가면 쌓은
결과가 통째로 사라진다.

**같은 인터프리터 안에서는 이 버그가 재현되지 않는다.** 회귀 테스트가 진짜
별도 프로세스를 띄우는 이유다 (`tests/test_paper_account_persistence.py`). 그때
스크립트를 파일로 실행하면 `sys.path[0]` 이 스크립트 폴더라 저장소가 안 잡히므로
`PYTHONPATH` 를 명시해야 한다.
